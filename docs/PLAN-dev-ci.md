# План: ветки, CI, тесты, покрытие и гейты

> Сводный план всего, что мы обсудили. Подготовлен к запуску через субагентов: у каждой
> кодовой задачи — самодостаточный промт, у прямых операций — точная команда.
> Порядок и зависимости — в §4.

---

## 1. Цели

1. Модель веток: `main` → `dev` → feature/fix-ветки; все изменения идут в `dev` через PR.
2. Автоматический прогон тестов в GitHub Actions при PR/push в `dev`.
3. Гейт «≤700 строк кода на файл» (комментарии **и пустые строки не считаются**).
4. Покрытие unit-тестами критичной чистой логики (`connect` уже есть; добавить `sshConfig`, `storage`, `keys`).
5. (Опционально) замер покрытия и порог.

---

## 2. Принятые решения (зафиксированы)

| # | Решение |

## 4. Карта задач и порядок

```
Этап 0 (прямые операции):  создать dev, default branch, protection      ← я делаю сам
        │
        ├─► Этап 1 (ПАРАЛЛЕЛЬНО, 3 субагента):
        │      A. Разделить renderer/app.js на модули
        │      B. Гейт 700 строк (scripts/check-line-limit.js) + правка CODE-RULES §1
        │      C. Unit-тесты для sshConfig.js / storage.js / keys.js
        │
        └─► Этап 2 (после A и B):
               D. GitHub Actions workflow (ci.yml: test + check:lines)
               E. (опц.) c8 + порог покрытия
```

Зависимости:
- **A, B, C** независимы → запускаются одновременно.
- **D** зависит от A (чтобы CI не падал на app.js) и от B (нужен `npm run check:lines`).
- **E** зависит от C (порог осмыслен после тестов).
- Этап 0 можно сделать сразу (до или параллельно с этапом 1).

## 5. Этап 0 — ветки (прямые операции, не субагент)

```bash
git checkout main && git pull
git checkout -b dev && git push -u origin dev

# D2 — dev как ветка по умолчанию:
gh repo edit --default-branch dev
```

Branch protection на `dev` (D4) настраивается в UI GitHub → Settings → Branches:
`dev` → «Require status checks to pass before merging» → чек `ci` (появится после этапа 2D).
Либо через `gh api` (после создания workflow).

## 6. Этап 1 — три параллельных субагента

Каждый промт — самодостаточный. Обязательное чтение перед кодом: `AGENTS.md`,
`CODE-RULES.md`, `UI-RULES.md` (для A), `WORKFLOW-RULES.md`. Рабочая директория — корень репозитория.

### 6.1. Субагент A — разделить `renderer/app.js`

```
Роль: coding-агент в репозитории «SSH Control» (Electron, macOS). Рабочая директория — корень.

Задача: разделить renderer/app.js (932 физические строки) на модули так, чтобы каждый
файл содержал ≤700 СТРОК КОДА (комментарии и пустые строки не считаются).

До кода прочитай: CODE-RULES.md §1 (лимит), §4 (рендер-конвенции), §7 (plain-JS);
UI-RULES.md; и сам renderer/app.js целиком.

ЖЁСТКИЕ ОГРАНИЧЕНИЯ (проект без бандлера, CSP script-src 'self'):
- Без бандлера, без ES-модулей, без import/export. Разбиение — обычными классическими
  <script>-файлами в renderer/, подключаемыми в index.html (порядок важен).
- Общий глобальный контекст, от которого зависит renderer/terminal.js, ДОЛЖЕН сохраниться:
  `state`, `$`, `$$`, `esc()`, `toast()`, `window.render`, `ICONS`, `PALETTE` и делегирование
  кликов по `data-action` — должны остаться доступны из других файлов тем же способом,
  что сейчас (классические скрипты делят глобальную lexical-область).
- Поведение НЕ менять: это чистый рефакторинг. Все экраны (ключи/псевдонимы/серверы/
  настройки/терминал) работают идентично. Никакой новой функциональности.
- Файлы ≤700 строк кода. Разбиение по смыслу (например: core + keys + aliases + servers +
  settings + modals), а не по номеру строки.

Как резать: оставь в одном «core»-файле bridge/state/хелперы/рендер-диспетчер и глобальный
обработчик data-action; экранные рендер-функции и их модалки вынеси в отдельные файлы,
которые определяют глобальные функции, вызываемые диспетчером/обработчиком.

Проверка:
- node --check для каждого нового .js;
- npm test (должно остаться 10/10 — тесты не покрывают рендер, но не сломай ничего);
- перечисли итоговый список файлов renderer/ и число строк кода в каждом (подтверди ≤700).

Формат результата: что вынесено куда; как сохранён общий контекст; список файлов + строки
кода; команды проверки; что осталось владельцу на ручной smoke (npm start).
```

### 6.2. Субагент B — гейт «≤700 строк кода» + правка CODE-RULES §1

```
Роль: coding-агент в «SSH Control». Рабочая директория — корень.

Задача: добавить гейт проверки лимита размера файлов и уточнить правило.

1) Новый файл scripts/check-line-limit.js (без новых npm-зависимостей):
   - обходит файлы main/**, renderer/**, test/**, scripts/** с расширениями .js, .html, .css;
   - ИСКЛЮЧАЕТ renderer/vendor/** (сторонние сборки xterm), node_modules/, dist/;
   - для каждого файла считает СТРОКИ КОДА = строки, содержащие хотя бы один
     не-пробельный символ вне комментария. Комментарии НЕ считаются, пустые строки НЕ считаются.
   - комментарии вырезаются корректно: JS/CSS — `//` и `/* … *‍/` с учётом строковых литералов
     ('' "" и template-литералов), HTML — `<!-- … -->`;
   - строка с кодом + хвостовым комментарием считается одной строкой кода;
   - файл с числом строк кода > 700 — нарушение. Вывести отчёт и завершиться exit 1.
2) В package.json добавить: "check:lines": "node scripts/check-line-limit.js".
3) В CODE-RULES.md §1 заменить формулировку лимита на: «≤700 строк кода (комментарии и
   пустые строки не считаются)» — это решение владельца отменяет прежнее «пустые считаются».

Проверка: node --check scripts/check-line-limit.js; npm run check:lines.
Ожидаемо сейчас выдаст нарушение для renderer/app.js (932 строки) — это нормально: app.js
разделяется отдельной задачей (субагент A), гейт в CI подключается ПОСЛЕ неё.
Формат результата: что сделано; пример вывода команды; список файлов-нарушителей на текущий момент.
```

### 6.3. Субагент C — unit-тесты для sshConfig / storage / keys

```
Роль: coding-агент в «SSH Control». Рабочая директория — корень.

Задача: добавить unit-тесты (node:test, без новых зависимостей) на чистую логику, перечисленную
в CODE-RULES.md §9.1. Тесты в test/ (по аналогии с test/connect.test.js).

Покрыть:
- main/services/sshConfig.js: parse / splitOptions / buildBlock / serialize. Главный кейс —
  «чужой» контент конфига (комментарии, Include, незнакомые опции, preamble) сохраняется

- main/services/storage.js: defaultData; setMasterPassword + unlock round-trip на ВРЕМЕННОЙ папке;
  lock() сбрасывает данные; save() в зашифрованном режиме. Не трогать реальный ~/SSH Control.

Ограничения (CODE-RULES §8.4, §9): фикстуры без реальных ключей/паролей; временные каталоги
(os.tmpdir + уникальный суффикс, очистка после теста); секреты не в git и не в логах.

Проверка: npm test — все тесты зелёные (10 старых + новые).
Формат результата: какие функции покрыты, сколько тестов добавлено, вывод npm test (pass/fail).
```

## 7. Этап 2 — CI и покрытие (после A и B)

### 7.1. Субагент D — GitHub Actions workflow

```
Роль: coding-агент в «SSH Control». Рабочая директория — корень.

Задача: создать .github/workflows/ci.yml, который при PR в dev и push в dev:
1. checkout (actions/checkout@v4);
2. setup-node с Node 20 (actions/setup-node@v4, node-version: 20);
3. npm ci --ignore-scripts  (тесты используют только встроенные модули Node; --ignore-scripts
   пропускает скачивание Electron ~100МБ и сборку node-pty — так CI быстрее);
4. npm test;
5. npm run check:lines.

Триггеры:
on:
  pull_request: { branches: [dev] }
  push: { branches: [dev] }

Ограничения: без секретов; YAML валидный; job на ubuntu-latest; осмысленное имя (ci).
Проверка: синтаксис YAML (можно проверить парсером), локально прогнать не получится — отметь это.
Формат результата: файл ci.yml и пояснение шагов.
```

### 7.2. Субагент E (опционально, D3) — c8 + порог покрытия

```
Роль: coding-агент в «SSH Control». Рабочая директория — корень.

Задача: добавить замер покрытия и порог.
1) devDependency "c8" (npm i -D c8); скрипт "coverage": "c8 npm test".
2) Порог 80% по строкам только для main/ (рендер и системные модули исключаем):
   c8 настроить через .c8rc.json или флаги (--reporter=text --reporter=lcov
   --exclude=renderer/** --exclude=test/** --lines=80).
3) В .github/workflows/ci.yml добавить шаг npm run coverage (сразу после npm test).
4) Покрытие НЕ должно ломать CI, если threshold не достигнут из-за непокрытых I/O-функций, —
   поэтому порог ставится на реально измеримую чистую логику; если c8 показывает меньше 80%
   по объективным причинам, зафиксируй фактическое значение в отчёте, а не поднимай ложный pass.

Формат результата: что добавлено; фактический % покрытия по main/; команды; отклонения.
```
