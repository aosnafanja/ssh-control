## 1. Цель и позиционирование

**Боль.** Сейчас SSH Control умеет хранить ключи/серверы/псевдонимы и подключаться по
SSH во встроенном терминале. Для работы с файлами на сервере пользователь вынужден
открывать терминал и вручную набирать `scp`/`rsync`/`sftp`, либо держать отдельный
клиент (Termius, Royal TSX, SecureCRT, electerm, WindTerm — у всех есть файловый
менеджер, см. `docs/ROADMAP-terminal.md` P2 #13).

**Что даёт фича.** Встроенный SFTP-файловый менеджер: подключиться к уже сохранённому
серверу → увидеть листинг удалённой директории → скачать/загрузить файл → видеть
прогресс и ошибки. Вертикальный срез «листинг + скачивание/загрузка + прогресс/отмена»
закрывает 80% повседневных сценариев («забрать лог», «положить конфиг», «скачать
бэкап») без выхода из приложения.

**Отличие от конкурентов.** Не «ещё один SFTP-клиент», а продолжение УТП SSH Control:
файлы открываются **по уже сохранённому серверу** (хост/порт/пользователь/ключ/пароль
уже в хранилище) — то же связывание хранилища с функцией, которое уже дал P0-терминал.
Без аккаунта, без телеметрии, локально.

## 2. Контекст (что переиспользуем)

| Что | Откуда | Как используем |
|---|---|---|
| Данные сервера `{ id, name, group, host, port, user, authMethod, keyPath, password, color, notes, extraArgs }` | `storage.getData()` → `data.servers` | SFTP-сессия строится из `host/port/user/keyPath/password` |
| Расшифрованный пароль сервера | уже в памяти main (`storage.js`) | `password` для ssh2 — **без** передачи через IPC |
| Ключи `~/.ssh` | `keys.js` (`sshDir`) | main читает приватный ключ как `Buffer` для ssh2 |
| `~/.ssh/known_hosts` | новый парсер | host key verification (§7) |
| Сборка подключения | `connect.js` `expandTilde`, `buildArgs` | переиспользуем `expandTilde`; `buildArgs` (argv для `ssh`) для SFTP **не** подходит — ssh2 принимает объект конфига, не argv |
| Паттерн сервиса с событиями | `main/services/terminal.js` (`setEventSink`, `emit`, `safeId`) | аналог для `sftp.js` (сессии/трансферы/события в рендер) |
| Паттерн «секция + модуль рендера» | `renderer/terminal.js`, `renderer/servers.js` | `renderer/files.js` по тем же конвенциям (`$`, `esc`, `state`, `data-action`) |
| Диалоги выбора/сохранения | `main.js` (`dialog.showOpenDialog`/`showSaveDialog`) | локальный файл для загрузки/скачивания выбирается **в main**, путь не пересекает IPC |
| Токены/классы/грамматики | `renderer/styles.css`, `UI-RULES.md` | таблица, тулбар, очередь, модалки — на существующих токенах |

## 3. Границы

### 3.1. Входит в v1 (минимальный полезный вертикальный срез)

1. **Подключение** к **серверу** (`data.servers`, не к псевдониму) по
   `host/port/user` + (`keyPath` | `password`). Сессия в main, одна на сервер.
2. **Листинг** удалённой директории: имя, тип (файл/каталог/симлинк), размер, права
   (`drwxr-xr-x`), время изменения. Навигация: вход в каталог, «Вверх», «Домой»,
   «Обновить», переключатель «показывать скрытые».
3. **Скачивание файла** на локальный диск (путь — через `dialog.showSaveDialog`).
4. **Загрузка файла** с локального диска (путь — через `dialog.showOpenDialog`) в
   текущую удалённую директорию.
5. **Прогресс и отмена** каждого файла + **очередь** трансферов (FIFO, по одному файлу
   за раз на сессию), завершение/ошибка с сообщением.
6. **Операции с каталогами:** создать папку, удалить пустую папку, удалить файл
   (с подтверждением).
7. **Host key verification** по `~/.ssh/known_hosts` с безопасным дефолтом (§7.1).
8. **Множественная загрузка** (решение владельца 27.11.2026): диалог выбора с
   `multiSelections` → все выбранные файлы добавляются в очередь.

### 3.2. Явно НЕ входит в v1 (и почему)

| Исключено | Почему |
|---|---|
| SFTP для **псевдонимов** (`Host` из `~/.ssh/config`) и `ProxyJump`/`ProxyCommand`/`Include` | ssh2 **не читает** `~/.ssh/config` и не поддерживает jump-hosts; тихое игнорирование ProxyJump = соединение не с тем хостом (риск). См. открытые вопросы §13 |
| `extraArgs` сервера для SFTP | те же причины: `-J`, `-o ProxyJump`, `ControlPath` и прочее не применимы к ssh2. Отображаем предупреждение, не применяем |
| **Рекурсивная** загрузка/скачивание каталогов | обход дерева, циклы симлинков, частичные состояния — отдельная сложность. v1 = только одиночные файлы |
| Drag-and-drop из Finder | дорого в смысле edge-кейсов; v1 покрывается диалогами. Механизм (`webUtils.getPathForFile`) задокументирован в §9.4 как дешёвый next-step |
| Двухпанельный (локальная + удалённая) браузер | дублирует Finder и удваивает surface edge-кейсов. v1 = одна удалённая панель + нативные диалоги |
| Rename/move/chmod/симлинк-операции, поиск по файлам, **множественное скачивание** (multi-select удалённых), resume/pause | расширяют scope без роста ценности среза |
| keyboard-interactive / 2FA / password+OTP | ssh2-обработка интерактивных промптов — отдельная работа; не проверено (§13) |
| Переиспользование ControlMaster-соединения терминала | отдельное TCP-соединение на SFTP; мux — сложность и хрупкость, не оправдана для v1 |
| Хранение сессий/очереди в `data.json` | сессии и очередь — эфемерны, живут в памяти main; персист не нужен |

## 4. Пользовательские сценарии + критерии приёмки

### Сценарии

1. **Подключение и листинг.** Пользователь открывает «Файлы», выбирает сервер из
   списка, жмёт «Подключиться» → видит содержимое домашней директории.
2. **Навигация.** Двойной клик по каталогу → вход; «Вверх»/«Домой»; «Обновить».
3. **Скачивание.** Выбирает файл → «Скачать» → диалог сохранения → прогресс →
   файл на диске.
4. **Загрузка (в т.ч. нескольких файлов).** «Загрузить» → диалог с `multiSelections` →
   каждый выбранный файл добавляется в очередь → прогресс → файлы в текущей папке.
5. **Отмена и очередь.** Несколько трансферов подряд в очереди; активный можно отменить;
   ошибка одного не роняет сессию и не мешает следующему.
6. **Host key.** Первый вход на новый хост → модалка с SHA256-отпечатком и выбором
   «принять на сессию» / «доверять и записать» / «отмена». Изменённый ключ → блок +
   предупреждение MITM.
7. **Ошибки.** Нет соединения / неверный пароль / отказ в правах / диск полон —
   понятное сообщение, сессия/очередь в консистентном состоянии.

### Проверяемые критерии приёмки

- [ ] `npm start` запускается; «Файлы» доступны из сайдбара.
- [ ] Подключение к серверу по ключу (без passphrase или ключ в ssh-agent) даёт листинг.
- [ ] Подключение к серверу по паролю (из хранилища) даёт листинг.
- [ ] Скачивание и загрузка файла(ов) показывают прогресс; отмена останавливает трансфер.
- [ ] Множественная загрузка: 2+ файла из одного диалога попадают в очередь и проходят по одному.
- [ ] Очередь: N файлов обрабатываются по одному; ошибка не ломает очередь.
- [ ] Неизвестный host key → модалка с отпечатком; «принять на сессию» работает без записи;
      «доверять» дописывает `known_hosts`; изменённый ключ блокируется.
- [ ] Пароль сервера и содержимое приватного ключа не появляются в рендере/логах (§7).
- [ ] `npm run package` собирается; SFTP работает в собранном `.app`.
- [ ] Чистые функции покрыты `node:test` (RED→GREEN), §10.
- [ ] Ни один файл не превышает 700 строк; UI-чеклист `UI-RULES.md` §9.2 пройден.

## 5. UX/UI: текстовый скелет (UI-RULES §9.1)

**Вопросы читателя:** «какие файлы на сервере», «как забрать/положить файл», «идёт ли
трансфер и не застрял ли».

**Решение по размещению:** **отдельный раздел «Файлы» в сайдбаре** (между «Терминал» и
«Настройки»), а не панель внутри терминала. Обоснование: SFTP — отдельный режим работы
со своим тулбаром, таблицей и очередью; вкладка терминала не даёт места и смешивает две
разные модели (поток вывода vs. структурированный листинг). Грамматика — новая
(по UI-RULES §4.3 допустима как осознанное решение, аналогично терминалу §4.7).

### Состав экрана `view-files`

- **`view-header`:** заголовок «Файлы», подзаголовок `.muted` «SFTP по сохранённому
  серверу». Справа (`header-actions`): `<select>` сервера (из `state.data.servers`,
  опции `name`), кнопка `.btn.primary` «Подключиться» / «Отключиться» (меняется по
  состоянию).
- **Тулбар (строка под заголовком):** путь (`.mono`, breadcrumb как текст
  `/home/user/...`), иконки-кнопки «Вверх»/«Домой»/«Обновить» (`.icon-btn`,
  `aria-label`+`title`), переключатель «Скрытые» (`.chip`/`.segmented`), `.btn.ghost`
  «Новая папка», `.btn.primary` «Загрузить», `.btn` «Скачать» (активна при выбранном
  файле).
- **Таблица (`.view-body`):** колонки Имя (иконка каталога/файла + имя), Размер, Права,
  Изменён. Строка — `role="row"`; каталог — двойной клик для входа; файл — одиночный
  клик для выбора (v1: single-select). Сортировка по умолчанию — каталоги первыми, затем
  по имени (вычисляется в main, §6).
- **Очередь (панель внизу секции):** список трансферов: направление (↓/↑), имя, прогресс-
  бар, «N / M», кнопка отмены (×), статус (готово/ошибка/отменено); «Очистить
  завершённые».
- **Модалки (`.modal`):** подтверждение host key (§7.1); «Новая папка» (поле имени);
  подтверждение удаления; подтверждение перезаписи при скачивании (если файл существует).
- **Пустые состояния (`.empty`):** «Выберите сервер и нажмите Подключиться» (нет
  соединения); «Папка пуста» (пустой листинг); «Трансферов нет» (пустая очередь).

### Состояния

Соединение: `нет соединения` / `подключение` / `подключено` / `ошибка` / `разорвано`.
Трансфер: `ожидание` / `активен` / `завершён` / `ошибка` / `отменён`. Показываются
бейджем `.badge` (статус — словом, не цветом; UI-RULES §3 п.5) и `aria-live` для ошибок.

### Ошибки

Хост недоступен, таймаут handshake, отказ аутентификации, host key изменён, диск полон,
нет прав на удалённый путь, файл занят. Все — тост `.toast.error` + текст в очереди;
секреты в тексте ошибки не появляются (§7.6).

### Имена файлов — недоверенный ввод

Имя файла с сервера может содержать любые символы, включая HTML и переводы строк.
Требования: рендер только через `esc()`/`textContent`; управляющие символы и `\n`/`\r`
в ячейке заменяются видимым представлением (или отбрасываются); имена не вставляются в
`title`/`aria-label` без экранирования; сортировка и сравнение — по исходной строке,
не по отображению.

### Доступность (UI-RULES §7)

Таблица с `role="table"`/`row` и клавиатурной навигацией (стрелки, Enter — войти/выбрать);
иконки-кнопки с `aria-label`+`title`; прогресс-бар с `role="progressbar"` + `aria-valuenow`;
фокус видим; контраст AA в обеих темах; Esc закрывает модалки.

### Явный список «чего на экране НЕТ»

Локальной панели браузера, drag-and-drop-зоны, поиска по файлам,
контекстного меню, renaming по месту, чекбоксов массовых операций, resume/pause.

## 6. Архитектура

### 6.1. Слои и новые файлы

```
main/services/sftp.js        ssh2-сессии, трансферы, hostVerifier-обвязка (требует ssh2)
main/services/knownHosts.js  парсер/матчер/сериализатор known_hosts (чистые функции)
main/services/sftpPath.js    posix-пути, сортировка, формат размера/прав/даты, isHidden (чистые)
main/services/sftpQueue.js   редуктор очереди трансферов (чистая функция)
main/main.js                 registerIpc(): + sftp-каналы (тонкие делегаты)
main/preload.js              window.api: + sftp-методы (прокси без логики)
renderer/files.js            рендер секции «Файлы», обработчики, события (≤700 строк)
renderer/index.html          + <section id="view-files"> + <script src="files.js">
renderer/styles.css          + классы таблицы/тулбара/очереди (при риске >700 строк — renderer/files.css)
```

`renderer/app.js` меняется точечно: пункт навигации `data-view="files"` в `render()` и
обработчик `nav`. Общая `state` и хелперы (`$`, `esc`, `toast`) — глобально из `app.js`
(как в `terminal.js`).

### 6.2. Жизненный цикл сессии (main)

1. `sftp:connect({ serverId })` → main ищет сервер в `storage.getData()`, валидирует
   `host/port/user`, читает ключ/пароль, создаёт ssh2 `Client`, `hostVerifier` →
   `knownHosts`, по `ready` открывает `client.sftp()` и возвращает `{ sessionId, home }`.
2. Сессия хранится в `Map<sessionId, { client, sftp, serverId, connectedAt, lastAt }>`.
   `sessionId` генерируется в main (`safeId`-подобный).
3. Idle-таймаут: сессия без активности > `SFTP_IDLE_TIMEOUT_MS` (предлагаем 5 мин) —
   закрывается; **активный трансфер обновляет `lastAt`** (idle не рвёт передачу);
   `keepaliveInterval` по умолчанию 0 (не шлём keepalive), `readyTimeout`
   по умолчанию 20 с (дефолт ssh2). Точные значения — открытый вопрос §13.
4. Закрытие: `sftp:disconnect`, повторный connect (закрыть старую), `app.quit`/закрытие
   окна → закрыть все сессии и отменить активные трансферы (аналог `terminal.killAll()`).

### 6.3. IPC-каналы и события

Правило: локальные абсолютные пути **не пересекают IPC**. Диалоги выбора/сохранения
открываются **в main** внутри обработчиков upload/download; рендер передаёт только
`sessionId`, удалённый путь/имя.

| Канал (invoke) | Аргументы | Возврат | Ошибки |
|---|---|---|---|
| `sftp:connect` | `{ serverId }` | `{ sessionId, home }` | сервер не найден / auth / host-key (см. событие) |
| `sftp:disconnect` | `sessionId` | `true` | — |
| `sftp:list` | `sessionId, dir` | `{ dir, entries[] }` (отсортировано, с `hidden`, `sizeText`, `modeText`, `mtimeText`) | сессия отсутствует / SFTP-ошибка |
| `sftp:mkdir` | `sessionId, dir, name` | `{ name }` | недопустимое имя / существует |
| `sftp:rmdir` | `sessionId, dir, name` | `true` | не пуста / отказ прав |
| `sftp:unlink` | `sessionId, dir, name` | `true` | отказ прав |
| `sftp:upload` | `sessionId, dir` | `{ transfers: [{ transferId, name, size }] }` (диалог с `multiSelections`) или `{ canceled: true }` | диалог отменён / файлы недоступны |
| `sftp:download` | `sessionId, dir, name` | `{ transferId }` или `{ canceled: true }` | диалог отменён / нет прав |
| `sftp:cancel` | `transferId` | `true` | трансфер завершён |
| `sftp:host-key-decision` | `sessionId, decision` (`accept-once`/`trust`/`reject`) | `true` | нет ожидающего решения |

События (`webContents.send`, парные `ipcRenderer.on` в preload):

| Событие | Аргументы |
|---|---|
| `sftp:progress` | `(transferId, transferred, total)` |
| `sftp:transfer-done` | `(transferId, status, errorMessage?)` — `ok`/`error`/`canceled` |
| `sftp:session-closed` | `(sessionId, reason)` |
| `sftp:host-key` | `(sessionId, { fingerprint, keyType, host, status })` — `unknown`/`changed`; рендер показывает модалку |

Ответ на host key рендер шлёт отдельным каналом `sftp:host-key-decision`
`(sessionId, decision)` — `accept-once` | `trust` | `reject`. Сам отпечаток/ключ —
метаданные, не секрет.

### 6.4. Состояние и данные

- **`data.json` — без изменений в v1.** Сервер уже содержит всё нужное. Новых полей и
  персиста сессий/очереди нет.
- **Host key доверие** — в `~/.ssh/known_hosts` (стандарт), не в `data.json`.
- **Сессии и очередь** — только в памяти main (`Map`); рендер держит зеркало для UI из
  событий.

## 7. Безопасность

### 7.1. Host key verification (MITM) — обязательный безопасный дефолт

ssh2 по умолчанию **авто-принимает** host key, если `hostVerifier` не задан (проверено
по исходникам — `kex.js`: `Host accepted by default (no verification)`). Это неприемлемо:
обязательно задаём `hostVerifier`.

Механика (в main):

1. `hostVerifier(key, verify)` получает **сырой host key blob** (`Buffer`) — тот же,
   что лежит в `known_hosts` в base64 (проверено: `kex.js` передаёт `readString()`
   host key blob; `hostHash` НЕ задаём, чтобы иметь сырой ключ для сравнения).
2. Считаем отпечаток: `SHA256(key)` → base64 → `SHA256:...` (совпадает с OpenSSH).
3. Читаем `~/.ssh/known_hosts`, ищем совпадение для `host` и `host:[port]`
   (поддержка обычных и хэшированных строк `|1|salt|hmac-sha1`).
4. Результат `matchKnownHosts(...)`:
   - `ok` (ключ совпал) → `verify(true)`.
   - `changed` (тот же host, другой ключ) → `verify(false)` + событие `sftp:host-key`
     со статусом `changed` (пользователь видит предупреждение; «принять на сессию» в v1
     для изменённого ключа **не предлагается** — только отмена).
   - `unknown` → НЕ `verify(false)` сразу: пауза, событие `sftp:host-key` со статусом
     `unknown`, рендер показывает модалку с отпечатком; после `sftp:host-key-decision`
     main вызывает `verify(true)` (accept-once — без записи) или `verify(true)` +
     дописывает строку в `known_hosts` (trust), или `verify(false)` (reject).
5. Важно: `verify(...)` вызывается **ровно один раз** и только после решения —
   иначе ssh2 зависнет в handshake. Ожидание решения ограничено (предлагаем 60 с):
   нет ответа → `verify(false)`, сессия не создаётся.
6. Запись «доверять» в `known_hosts` — **append-only**: файл не переписывается и не
   усекается, чужие строки сохраняются verbatim; запись атомарная (временный файл в
   `~/.ssh` + rename), права файла не теряются, дубликат строки не добавляется. Если
   запись не удалась — соединение всё равно продолжается (accept-once), пользователь
   получает предупреждение (не блокируем работу из-за прав на `known_hosts`).

Безопасный дефолт: **неизвестный ключ — блок до явного решения; изменённый ключ — блок
без «принять»**. Запись в `known_hosts` — только явным «доверять».

### 7.2. Аутентификация без нарушения инвариантов

ssh2 работает **в main**, поэтому весь секретный материал остаётся в main и **не
пересекает IPC** — это соответствует инвариантам AGENTS.md.

- **`authMethod: 'password'`** → пароль берётся из уже расшифрованного
  `storage.getData()` (в памяти main), передаётся в ssh2 `password`. Рендер не участвует.
- **`authMethod: 'key'`** → main читает приватный ключ (`~/.ssh/<keyPath>`) как `Buffer`
  и передаёт в ssh2 `privateKey` (приватный материал остаётся в main).
- **ssh-agent** → если ключ загружен в macOS ssh-agent, можно использовать
  `agent: process.env.SSH_AUTH_SOCK` (без чтения ключа и без passphrase). Рекомендация:
  в v1 для ключа **сначала** пробуем agent, затем unencrypted-ключ.
- **Ключ с passphrase** — passphrase в app **не хранится** (AGENTS.md), а передавать его
  из рендера через IPC запрещено инвариантом «парольная фраза ключа через IPC не
  передаётся никогда». Поэтому **v1: ключи с passphrase, не загруженные в ssh-agent,
  блокируются** с сообщением «загрузите ключ в агент: `ssh-add ~/.ssh/<key>`».
  Ввод passphrase в модалке = осознанное ослабление инварианта → **открытый вопрос
  владельцу** (§13), не принимается молча.

**Связанный известный дефект.** Пароль сервера хранится в `data.json` и шифруется
мастер-паролем; при **отключённом** шифровании он лежит открыто — это Maintenance-баг
#37. SFTP не ухудшает ситуацию (пароль читается в main и не пересекает IPC), но #37
желательно закрыть до релиза SFTP; см. открытые вопросы §13.

### 7.3. Path traversal и локальные пути

- Рендер **не** передаёт локальные абсолютные пути. Локальный путь для скачивания —
  `dialog.showSaveDialog`, для загрузки — `dialog.showOpenDialog`, оба в main.
- Удалённый путь строится **в main**: `joinRemotePath(currentDir, name)` (posix-join с
  нормализацией), имя приходит из листинга сервера или из `mkdir` (санитизируется —
  запрет `..`, `/`, управляющих символов).
- Имя при скачивании: `sftp:download(sessionId, dir, name)` — main валидирует `name` как
  единичный сегмент (без `/`, `..`), путь = `joinRemotePath(dir, name)`.

### 7.4. Симлинки и рекурсия

- Рекурсивных операций в v1 нет (передача только одиночных файлов) → риск обхода через
  симлинки каталогов на удалённой стороне неактуален.
- Симлинк в листинге отображается как отдельный тип (через `lstat`); операции с ним
  (загрузка/скачивание/удаление) в v1 **не выполняются** — строка некликабельна для
  трансфера (только отображение). Причина: неоднозначное поведение `fastGet`/`fastPut`
  по симлинкам на разных SFTP-серверах.

### 7.5. Лимиты и ресурсы

- Файлы передаются **потоком** (`fastGet`/`fastPut` с локальным `fs`-стримом), а не
  загрузкой целиком в память → большие файлы не съедают RAM.
- Очередь в main ограничена (`SFTP_MAX_QUEUE`, предлагаем 100) — сверх лимита отказ.
- `readyTimeout` (20 с) и idle-таймаут сессии — против зависших соединений.
- Без ограничения размера файла в v1 (диск пользователя); при желании — позже.

### 7.6. Что НЕ уходит в рендер и в логи

Приватный ключ, пароль сервера, passphrase, сырой host key blob, локальные абсолютные
пути, содержимое `data.json`. В сообщения об ошибках не подставляются пароль/passphrase/
имя файла ключа. CSP не меняется; новых рендерных зависимостей нет (таблица — vanilla
HTML/CSS/JS, без vendor-файлов).

## 8. Краевые условия и ошибки

| Условие | Поведение |
|---|---|
| Сервер не отвечает / порт закрыт | ошибка подключения, тост, сессия не создана |
| Handshake таймаут (`readyTimeout`) | ошибка, закрыть сокет |
| Неверный пароль / отклонён ключ | ошибка аутентификации (без секрета в тексте) |
| Host key `unknown` | модалка, блок до решения |
| Host key `changed` | блок, предупреждение MITM |
| Пустая директория | `.empty` «Папка пуста» |
| Каталог с отказом в правах при `readdir` | ошибка в панели листинга, путь остаётся |
| Файл уже существует при скачивании | подтверждение перезаписи (dialog/модалка) |
| Диск заполнен при скачивании | ошибка трансфера, частичный файл удаляется |
| Отмена активного трансфера | закрыть стрим, статус `canceled`, очередь идёт дальше |
| Разрыв соединения во время трансфера | трансфер в `error`, сессия в `разорвано`, предложение переподключиться |
| `unlink`/`rmdir` с отказом | тост-ошибка, листинг не портится |
| Окно закрыто во время трансфера | `killAll()`: отмена трансферов + закрытие сессий |

## 9. Технические решения

### 9.1. Сравнение транспорта

| Критерий | (A) ssh2 (npm, pure JS) | (B) системный `sftp`/`scp`/`rsync` (spawn) | (C) ControlMaster/ssh mux |
|---|---|---|---|
| Безопасность (host key) | свой `hostVerifier` по known_hosts (пишем сами) | OpenSSH проверяет сам (надёжно, «бесплатно») | OpenSSH (как B) |
| Прогресс / отмена | нативные `fastGet`/`fastPut` c `step()`, отмена через destroy стрима | `rsync --progress`/`--info` (парсить текст, хрупко); `scp`/`sftp` — почти нет | как B |
| Аутентификация | программно в main: password/privateKey/agent — секрет не через IPC | пароль через tty/stdin хрупко (нет sshpass на macOS); passphrase — agent/askpass | как B |
| Упаковка electron-builder | pure JS + optional native с fallback; `dependencies` уже собираются (node-pty-прецедент) | без новых зависимостей | без новых зависимостей |
| Тестируемость | чистые функции (known_hosts, пути, очередь) юнитятся | spawn/парсинг — только smoke | низкая (сокеты/расы) |
| `~/.ssh/config`, ProxyJump, Include, ControlMaster | **не поддерживаются** | полная поддержка | полная поддержка |

**Выбор: (A) ssh2.** Единственный вариант, дающий честные прогресс/отмену и
программную аутентификацию без секрета через IPC или spawn с argv/паролем. Цена —
отсутствие `~/.ssh/config`/ProxyJump — закрывается границей v1 (§3.2: только серверы,
без `extraArgs`). Host key verification реализуем сами — это основной новый
безопасный код, покрывается unit-тестами. (B)/(C) оставляют проблему пароля/progress и
не дают отмены уровня стрима.

### 9.2. Зависимости и упаковка (проверено)

- `ssh2@1.17.0` (`engines: node >=10.16.0`). **dependencies:** `asn1 ^0.2.6`,
  `bcrypt-pbkdf ^1.0.2`. **optionalDependencies:** `nan ^2.23.0`, `cpu-features ~0.0.10`.
- `cpu-features` — нативный (install: `node-gyp rebuild`); `bcrypt-pbkdf` — чистый JS
  (`tweetnacl`). Дополнительно ssh2 имеет собственный опциональный нативный биндинг
  `sshcrypto.node` (строится `install.js`).
- **Влияние `npmRebuild:false`:** оба нативных биндинга загружаются в try/catch и при
  сбое падают в pure-JS реализацию (`constants.js`: `try { require('cpu-features') } catch {}`;
  `crypto.js`: `try { require('./crypto/build/Release/sshcrypto.node') } catch {}`). Вывод:
  ssh2 **работает как pure JS**; `npmRebuild:false` не ломает SFTP (чуть медленнее bulk-
  crypto, компенсируется Node-OpenSSL). ФАКТ (по исходникам tarball), но фактический
  запуск в собранном `.app` — **НЕ ПРОВЕРЕНО** (§13).
- **Включение в сборку:** electron-builder уже кладёт production-`dependencies` в asar,
  а нативные — в `app.asar.unpacked` (прецедент `node-pty`; `builder-debug.yml`:
  `nodeModuleFilePatterns` включает `**/*`). Значит `ssh2` + чистые зависимости попадут
  в `.app` после добавления в `dependencies`. CI (`npm ci --ignore-scripts`) не ломается:
  install-скрипт ssh2 пропускается (он опциональный), а unit-тесты чистых функций ssh2
  не требуют.

### 9.3. Прогресс / отмена

- Прогресс: `fastGet`/`fastPut` с `opts.step(transferred, chunk, total)` → `emit('sftp:progress', ...)`,
  троттлинг ~100–200 мс, чтобы не заваливать IPC.
- Отмена: `transferId` → закрытие локального/удалённого стрима и `client`-объекта
  трансфера; статус `canceled`. Отмена не трогает SSH-соединение.
- Очередь: main обрабатывает FIFO по одному файлу на сессию (`concurrency = 1` для
  трансферов; внутренний chunk-concurrency ssh2 остаётся дефолтным 64).

### 9.4. Drag-and-drop (next-step, не v1)

Механизм зафиксирован: preload через `contextBridge` + `webUtils.getPathForFile(file)`
(API проверен по `electron.d.ts` v45: `getPathForFile(file: File): string`; официальный
паттерн для contextIsolation) возвращает абсолютный путь локального файла; рендер шлёт
его в `sftp:uploadPath(sessionId, localPath, dir)`; main валидирует «абсолютный путь +
существует» перед чтением. В v1 не делаем (диалоги достаточны), но путь расширения ясен.

## 13. Решения владельца + проверенные факты

### Решения владельца (закрыты 27.11.2026)

1. **Passphrase-ключи вне ssh-agent** — остаётся **блок v1** с сообщением
   `ssh-add ~/.ssh/<key>`; модалка ввода фразы не делается, инвариант «секреты не через
   IPC» сохраняется без исключений.
2. **Граница подтверждена**: v1 — только «серверы» (host/port/user/key/password);
   псевдонимы, ProxyJump, Include и `extraArgs` — вне объёма (нужен резолвер
   `~/.ssh/config`, отдельный этап).
3. **Idle/keepalive/readyTimeout** — принято: idle 5 мин (активный трансфер держит
   сессию), `keepaliveInterval=0`, `readyTimeout=20 с`.
4. **Множественная загрузка** — **включается в v1**: `showOpenDialog` с
   `multiSelections`, все выбранные файлы добавляются в очередь; контракт `sftp:upload`
   возвращает массив трансферов (§6.3).
5. **Лимит очереди** — `SFTP_MAX_QUEUE = 100`, сверх лимита — отказ.
6. **Дефект #37** (пароль сервера открыто при выключенном шифровании) — **чинится до
   релиза SFTP**: релиз файлового менеджера не выпускается поверх незашифрованного пароля.
