# CODE-RULES.md — SSH Control: правила написания кода

> Нормативный документ: **как писать код** приложения — слои (main / preload / renderer),
> IPC, хранилище, чистый код, конвенции plain-JS, безопасная разработка, тесты, лимиты.
> Применяется ко всему новому коду без исключений; при конфликте с личными предпочтениями
> побеждает он. Каждое правило — в форме «правило → зачем → чем охраняется» (тест, ревью,
> или инвариант кода).
>
> Чего здесь нет: обзор проекта, стек и ограничения платформы — `AGENTS.md`; интерфейс и
> взаимодействие — `UI-RULES.md`; процесс (задачи в GitHub, ревью, DoD, релиз) —
> `WORKFLOW-RULES.md`.

---

## 1. Структура и зоны ответственности

```
main/                привилегированный процесс (Node): ФС, дочерние процессы, криптография
  main.js              точка входа и жизненный цикл + registerIpc()
  preload.js           тонкий мост window.api (contextBridge)
  services/            по одному модулю на зону ответственности
renderer/            непривилегированный интерфейс: HTML/CSS/vanilla JS
build/               иконки и ресурсы сборки (не код приложения)
```

| Слой | Что содержит | Что запрещено |
|---|---|---|
| `main/services/*` | Работа с `~/.ssh`, `~/.ssh/config`, `data.json`, сборка команд, запуск процессов | Знание о DOM; хранение состояния UI; дублирование логики другого сервиса |
| `main/main.js` | Создание окна, `registerIpc()`, подписки жизненного цикла | Бизнес-логика; доступ к ФС/данным напрямую мимо `services/` |
| `main/preload.js` | Мост `window.api`: `ipcRenderer.invoke`/`on` по одному методу на канал | Логика, вычисления, знание формата данных |
| `renderer/` | Состояние экрана, рендер, обработчики ввода | Прямой доступ к Node/ФС; `require`; работа с ключами/секретами |

> Правило «один файл = одна зона ответственности» держится ревью. Граница между
> main и renderer — техническая (contextIsolation), поэтому её нарушение невозможно
> случайно: оно возможно только сознательным расширением preload (см. §3).

**Лимит размера файла — ≤700 строк кода (комментарии и пустые строки не считаются)** для
любого `*.js`, `*.html`, `*.css`. Файл у порога делится по смыслу (новый модуль
в `services/`, новая секция стилей, вынесенный рендер-хелпер), а не сжимается.
Проверяется ревью (WORKFLOW-RULES §4).

## 2. Main-процесс: сервисы и слои

### 2.1. Организация по зоне ответственности, а не по типу

Каждая зона — отдельный файл в `main/services/`, со всем своим содержимым:

```
✅ main/services/keys.js        — скан, создание, переименование, удаление ключей
   main/services/sshConfig.js   — чтение/редактирование ~/.ssh/config
   main/services/storage.js     — data.json: загрузка/сохранение/шифрование
   main/services/connect.js     — сборка команды ssh, запуск Terminal

⛔ main/services/utils.js       — «свалка» разнородных хелперов без одной зоны
```

Раздел растёт — новый файл (`main/services/terminal.js` для P0), а не разбухающий
существующий.

### 2.2. `main.js` — только склейка

`main.js` создаёт окно и регистрирует IPC-обработчики; каждый обработчик — одна строка
делегирования в сервис:

```js
// ✅ тонкая регистрация:
ipcMain.handle('keys:create', (_e, opts) => keys.createKey(opts));
ipcMain.handle('data:unlock', (_e, password) => storage.unlock(password));

// ⛔ логика прямо в обработчике:
ipcMain.handle('keys:create', async (_e, opts) => {
  const safe = String(opts.name).replace(...);   // не здесь
  await fs.writeFile(...);                        // не здесь
});
```

Обращение к ФС, `child_process`, `crypto` из `main.js` напрямую — блокер ревью.

### 2.3. Взаимодействие с системой — через `execFile`/`spawn`, с массивом аргументов

Команды (`ssh-keygen`, `osascript`) выполняются через `execFile` с массивом аргументов,
а не через `exec` со строкой оболочки. Строка из пользовательского ввода (`extraArgs`,
имя ключа, комментарий) **никогда** не интерпретируется оболочкой — так закрывается
инъекция команд.

```js
// ✅ аргументы отдельно, оболочка не задействована:
await run('ssh-keygen', ['-t', type, '-f', target, '-q', '-N', passphrase || '']);

// ⛔ интерполяция пользовательского ввода в строку оболочки:
exec(`ssh-keygen -t ${type} -N "${passphrase}"`);   // инъекция и утечка фразы в ps
```

См. `keys.js` и `connect.js` как образцы. Подробнее — §8.

### 2.4. Границы сервисов

- Сервис экспортирует только свой публичный API через `module.exports`; внутренние
  хелперы (`parse`, `splitOptions`, `expandTilde`) наружу не отдаются без необходимости.
- **Запрещены глубокие импорты внутренностей чужого сервиса.** Общая константа
  (`sshDir`) живёт в одном файле-владельце (`keys.js`) и импортируется явно
  (`sshConfig.js` делает `require('./keys')`).

## 3. IPC и preload

### 3.1. Единственный мост — `window.api`

Рендер получает доступ к системе **только** через `window.api`, собранный в
`preload.js` через `contextBridge.exposeInMainWorld`. Прямого `ipcRenderer` в рендере нет
и быть не может (`nodeIntegration: false`).

### 3.2. Каждая возможность — один канал с неймингом `namespace:action`

- Канал: `keys:scan`, `data:unlock`, `sshconfig:save`, `connect:run`. Пространство имён —
  зона ответственности, действие — глагол.
- Каждому каналу соответствует ровно один метод в `preload.js` и ровно один
  `ipcMain.handle` в `registerIpc()`. События из main в рендер (`webContents.send`) —
  с парными `ipcRenderer.on` в preload (см. `onTermData`/`onTermExit` из P0).

### 3.3. preload — без логики

`preload.js` только проксирует: `(opts) => ipcRenderer.invoke('keys:create', opts)`.
Никаких вычислений, проверок полей, знание формата данных. Это держит поверхность
атаки минимальной и делает каждый метод аудируемым одной строкой.

### 3.4. Что проходит через IPC — минимально и без секретов

- В рендер отдаются **только метаданные ключа**: имя, путь, `pub`, отпечаток, bits,
  type, comment, mtime. Содержимое приватного ключа — никогда (см. `keys.js`).
- Аргументы из рендера (опции создания ключа, запись сервера) валидируются **в main**:
  имя ключа проходит `sanitizeName`, псевдоним — проверку на пробелы. Рендер не является
  доверенной границей.
- Новый обработчик добавляется с вопросом «нужны ли рендеру именно эти данные?»
  (AGENTS.md, «Проверять решения на риски»).

## 4. Renderer: vanilla JS + HTML + CSS

### 4.1. Конвенции (уже действуют в `app.js`)

- `'use strict'` в начале файла.
- `const bridge = window.api;` — единственная точка доступа к main.
- `const $ = (s) => document.querySelector(s);` / `const $$ = (s) => Array.from(document.querySelectorAll(s));`
- Единое состояние — объект `state`; рендер выводится из `state` функциями, а не
  мутирует DOM точечно где попало.
- Обработчики — через делегирование по `data-action` (`data-action="nav"`, `data-action="new-key"` …),
  а не навешиванием слушателей на каждый элемент в разметке.
- Хелперы экрана: `esc()` (экранирование HTML), `shorten()`, `fmtDate()`, `toast()`.

### 4.2. Любой пользовательский текст — через `esc()`

Всё, что приходит из данных (имя ключа, хост, путь, комментарий, вывод ssh), перед
вставкой в HTML проходит `esc()`. Значения, которые вставляются в атрибуты и в видимый
текст, — через `textContent`, не `innerHTML`. `innerHTML` — только для заранее
заданных шаблонов, где динамика уже экранирована.

```js
// ✅ экранирование:
return `<div class="key-name">${esc(k.name)}</div>`;

// ⛔ XSS:
el.innerHTML = '<div>' + server.host + '</div>';   // host из данных пользователя
```

### 4.3. Без inline-скриптов и внешних ресурсов

CSP `script-src 'self'` запрещает inline-`<script>` и CDN. Весь JS — отдельными файлами
в `renderer/`. Сторонние браузерные библиотеки (xterm.js и аддоны) — локальными файлами
(для P0 — `renderer/vendor/`), а не ссылкой на CDN (см. `docs/PROMPT-P0.md` §4.4).

### 4.4. Стили — классами, не inline

Оформление — классами из `styles.css`, а не `style="…"`. Исключение ровно одно:
**цвет категории из данных** (точка сервера, `--accent` для выбранного цвета) задаётся
через `style`, потому что палитра конечна и приходит из данных. Подробно — UI-RULES §1.

## 5. Хранилище данных

- **Единственная точка работы с `data.json` — `storage.js`.** Остальной код не трогает
  файл напрямую: `loadRaw`/`writeData` — приватные, наружу отдаются
  `getState`/`getData`/`unlock`/`save`/`setMasterPassword`.
- **Атомарная запись:** `writeData` пишет во временный файл `data.json.tmp` и делает
  `renameSync`, чтобы обрыв процесса не оставил битый JSON (это уже реализовано —
  не регрессировать).
- **Шифрование в одной точке:** AES-256-GCM, IV и auth-tag случайные на каждую запись,
  ключ из scrypt по мастер-паролю с солью. Параметры `SCRYPT_N/R/P` — константы, их
  понижение под «скорость» запрещено.
- **Мастер-пароль нигде не хранится** ни в открытом виде, ни в производном виде кроме
  как через `scryptSync`. Расшифрованные данные живут только в памяти (`let data`),
  `lock()` их сбрасывает.
- Схема данных версионируется (`version: 1`); смена схемы — отдельное решение
  (WORKFLOW-RULES §2.1), с обратной совместимостью через `normalizeData` в рендере.

## 6. Чистый код (по книге «Чистый код» Р. Мартина)

Ниже — обязательные правила, а не пожелания. Охраняются ревью (WORKFLOW-RULES §4).

### 6.1. Имена

- Имя раскрывает намерение: `isPrivateKeyFile`, `updateConfigReferences`, а не `f1`, `tmp2`.
- Одно понятие — одно слово на весь репозиторий: не смешивать `get`/`load`/`read` для
  одного действия. В `storage.js` — `getData`/`getState`; в `sshConfig.js` — `getHost`/`listHosts`.
- Константы — `UPPER_SNAKE_CASE` в файле-владельце (`SCRYPT_N`, `DATA_FILE`, `DEFAULT_DIR`).

### 6.2. Функции

- Маленькие функции, один уровень абстракции. `describeKey`, `sanitizeName`,
  `splitOptions` — хорошие образцы: каждый делает одно названное дело.
- ≤3 параметров; больше — объект-параметр с именованными полями
  (`createKey({ name, type, bits, comment, passphrase })`).

### 6.3. Комментарии

- Комментарий объясняет **почему**, а не **что**. «Что» обязан объяснять сам код.
- Запрещены закомментированный код (для этого есть git) и комментарии-дубликаты.
- Обязательные комментарии: обоснование отступления от правила, неочевидное доменное
  решение. Пример уже в коде: `sshConfig.js` объясняет, что «чужие» строки конфига
  сохраняются verbatim.

### 6.4. Ошибки

- Ошибки — исключениями, а не кодами возврата: `throw new Error('Ключ уже существует')`.
- **Запрещено возвращать `null` как признак «не нашлось/ошибка» без явной семантики.**
  Где «не найдено» — легитимный результат (`getHost` → `null`, `unlock` при неверном
  пароле → `null`), это документируется и обрабатывается на месте вызова; где это сбой —
  бросается исключение.
- **Boundaries:** внешние системы (`ssh-keygen`, `osascript`) обёрнуты сервисами, которые
  возвращают **наши** типы; сырой вывод внешней команды не покидает сервис без обработки.

### 6.5. DRY и абстракции

- Реальное дублирование устраняется (`expandTilde` в `connect.js`, `run` в `keys.js`).
- Преждевременная абстракция запрещена: обобщаем на третьем повторении, а не на первом
  «вдруг пригодится».

## 7. Конвенции plain-JS (решение проекта)

Проект сознательно без TypeScript и без бандлера: маленькое приложение, минимум
зависимостей, никакой сборки JS. Это решение не пересматривается без отдельной
договорённости (WORKFLOW-RULES §2.1).

- `'use strict'` в каждом файле.
- `const`/`let`; `var` запрещён. Неявные глобалы запрещены.
- Строки — одинарные кавычки; точки с запятой обязательны; 2 пробела отступа.
- `async`/`await` вместо вложенных колбэков; `Promise`-обёртки над `execFile`/`execFileSync`
  — в одном месте (`execFileP` в `connect.js`, `run` в `keys.js`), не дублируются.
- Публичные контракты сервисов — с кратким JSDoc (`@param`/`@returns`) там, где тип
  аргумента не очевиден из имени.
- Стрелочные функции — для колбэков и коротких выражений; `function` — для объявлений
  на верхнем уровне модуля (единообразие с существующим кодом).

## 8. Безопасная разработка (secure coding)

### 8.1. Границы процесса — не ослаблять

`contextIsolation: true`, `nodeIntegration: false`, CSP `script-src 'self'` — инварианты
(AGENTS.md). Любое их ослабление «под удобство» — блокер ревью.

### 8.2. Команды и инъекции

- Все внешние команды — через `execFile`/`spawn` с **массивом аргументов**, не через
  `exec` со строкой оболочки (§2.3).
- `extraArgs` — осознанная power-user-функция, но точка риска: она разбивается по
  пробелам и добавляется как отдельные аргументы `ssh`, а не как подстрока команды.
  Сырая интерполяция `extraArgs` в строку оболочки запрещена.
- Пароль/парольная фраза передаются процессу как **аргумент или через PTY**, но никогда
  не печатаются и не попадают в логи; при переходе на PTY (node-pty) пароль вводится
  пользователем в терминал, а не автозаполняется (`docs/PROMPT-P0.md` §3.2).

### 8.3. Пути и файловая система

- Имена файлов из ввода проходят санитизацию (`sanitizeName` в `keys.js`: убирает `../`,
  пробелы, спецсимволы) **до** превращения в путь.
- Пользовательский путь к папке хранилища приходит из системного диалога
  (`dialog.showOpenDialog`), а не из произвольной строки; путь ключа всегда строится
  от `sshDir`, а не от пользовательского имени.
- Запись в `~/.ssh/config` сохраняет чужой контент verbatim и меняет только управляемые
  `Host`-блоки (см. `sshConfig.js`).

### 8.4. Секреты

- **Никогда** в git: пароли, парольные фразы, содержимое ключей, `data.json`, реальные
  данные в фикстурах. `.gitignore` закрывает `node_modules/`, `dist/`, кэши.
- **Никогда** в логи и сообщения об ошибках, видимые пользователю/в консоли: мастер-пароль,
  пароль сервера, парольная фраза, приватный ключ.
- Приватный материал ключей не пересекает IPC (§3.4).

### 8.5. Криптография

- Использовать `crypto` Node, а не самописные примитивы. AES-256-GCM: случайный IV (12 байт)
  и auth-tag на каждую запись, ключ 32 байта из scrypt с случайной солью.
- Не понижать `SCRYPT_N/R/P`; не хранить мастер-пароль; не выводить ключ без соли.

### 8.6. XSS в рендере

- Любой текст из данных — через `esc()` или `textContent` (§4.2).
- Запрещены: inline-`<script>`, `eval`, `new Function`, `document.write`, внешние ресурсы.

## 9. Тестирование

### 9.1. Что тестируется unit-тестами

Тесты — через встроенный `node:test` (`node --test`, без новых зависимостей). Покрывать
**чистую логику**, которую можно проверить без UI и без реальных файлов:

- `sshConfig.js` — `parse`/`splitOptions`/`buildBlock`/`serialize` на фикстурных строках
  конфига (главный кандидат: сохранение «чужого» контента verbatim, округлый trip).
- `storage.js` — `defaultData`, `setMasterPassword` + `unlock` round-trip на временной
  папке, `lock` сбрасывает данные.
- `connect.js` — `buildCommand`/`buildAliasCommand` (порт, `-i`, `IdentitiesOnly`,
  `user@host`), `expandTilde`.
- `keys.js` — `sanitizeName`, `parseFingerprintLine`.
- Рендерные чистые хелперы (`esc`, `shorten`, `normalizeData`) — если их вынести в
  отдельный модуль.

Файлы, ходящие в реальную ФС/сеть/`ssh-keygen`, unit-тестами не трогаются — их проверяет
ручной smoke (см. ниже).

### 9.2. TDD для логики

Для изменений в перечисленных выше чистых функциях: RED (падающий тест) → GREEN
(минимальная реализация) → REFACTOR. Bugfix начинается с теста, воспроизводящего баг.
RED-тест обязан упасть с конкретной причиной — красный вывод приводится в PR как
доказательство (WORKFLOW-RULES §4).

### 9.3. Smoke-проверка UI и системы

UI и взаимодействие с `~/.ssh`/`ssh` unit-тестами не покрываются (нет Playwright,
браузерного e2e). Каждая задача с UI/системными изменениями проверяется вручную:
`npm start`, затем шаги из карточки. Для сборки — `npm run package` и запуск `.app`
из `dist/` (это ловит потерю файлов рендера и нативные модули).

### 9.4. Пороги покрытия

Порогов нет — тестовой инфраструктуры пока нет, и вводить их раньше тестов бессмысленно.
Когда тесты появятся, пороги добавляются вместе со скриптом `npm test` в `package.json`.

## 10. Явно запрещённые паттерны (сводная таблица)

| Запрещённый паттерн | Причина |
|---|---|
| Бизнес-логика или доступ к ФС в `main.js` / в обработчике IPC | main.js — только склейка (§2.2) |
| `exec` со строкой оболочки вместо `execFile`/`spawn` с массивом | Инъекция команд (§2.3, §8.2) |
| Приватный ключ / пароль / фраза через IPC в рендер | Минимизация поверхности утечки (§3.4) |
| `nodeIntegration: true` или снятие `contextIsolation` | Рушит всю модель безопасности (§8.1) |
| Расслабление CSP ради CDN или inline-скриптов | XSS / внешний код (§8.6) |
