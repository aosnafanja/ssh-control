# WORKFLOW-RULES.md — SSH Control: правила процесса разработки

> Нормативный документ: **как ведём задачи, ревью и релиз**.
> Как писать код — [`CODE-RULES.md`](./CODE-RULES.md). Интерфейс — [`UI-RULES.md`](./UI-RULES.md).
> Обзор проекта и стек — [`AGENTS.md`](./AGENTS.md).
>
> **Все задачи ведутся в GitHub** — Issues для задач, Pull Requests для изменений.
> Документ адаптирован из репозитория `BCS-TM-Platform` под GitHub и под десктоп-приложение:
> GitLab → GitHub, MR → PR, NestJS/Vue/TS → Electron/plain-JS, OKD-деплой → electron-builder.

---

## 1. Типы задач (GitHub labels)

| Тип | Label | Что это | TDD / ревью |
|---|---|---|---|
| Feature | `enhancement` | Новый функционал или доработка текущего | Да (CODE-RULES §9.2) |
| Bug | `bug` | Исправление ошибки | Да — сначала тест, воспроизводящий баг |
| Documentation | `documentation` | Только документация | Нет; гейт — зелёный рендер текста |
| Chore | `chore` | Инфраструктура, зависимости, рефакторинг без изменения поведения | По ситуации |
| Research / Spike | `research` | Исследование, сравнение подходов | Нет; результат — документ или вывод в задаче |
| Question | `question` | Вопрос, требующий решения владельца | Нет |

Некодовые задачи (documentation, research, question) не требуют TDD и код-ревью — их DoD
определяется в карточке при создании.

## 2. Жизненный цикл feature-разработки

> Спецификация → декомпозиция → Issues → исполнение → PR → ревью → закрытие.

### 2.1 Спецификация

Перед значимой фичей (например, P0-терминал) создаётся спека в `docs/`:
цель, контекст, границы (что явно НЕ входит), сценарии, краевые условия, безопасность,
критерии приёмки. Пример действующей спеки — [`PROMPT-P0.md`](./docs/PROMPT-P0.md),
дорожная карта — [`ROADMAP-terminal.md`](./docs/ROADMAP-terminal.md).

Спека — **источник истины**: при конфликте кода и спеки права спека; спорное уточняется
у владельца, а не решается молча. Решения владельца **после** сдачи спеки фиксируются
записью в спеке или комментарием в issue, а не теряются.

### 2.2 Декомпозиция

Фича декомпозируется на атомарные задачи. Критерий атомарности:

- одна задача = **один PR**;
- результат независимо проверяем (тестом или ручной проверкой на живом приложении);
- ориентир по объёму — не более ~1 дня работы;
- карточка self-contained: понятна без чтения соседних задач (нужный фрагмент спеки
  копируется в карточку + ссылка на спеку).

Дробить мельче нельзя: overhead карточек не должен превышать пользу от декомпозиции.

### 2.3 Задачи в GitHub

Задачи заводятся как **GitHub Issues** по шаблонам из `.github/ISSUE_TEMPLATE/`
(`feature.md`, `bug.md`). Обязательные элементы карточки:

- **Контекст** — зачем задача, ссылка на спеку;
- **Что нужно сделать** — конкретный, проверяемый результат;
- **DoD** — чеклист (§4);
- **Labels** — тип (§1) + раздел `area:*` (§5);
- **Milestone** — этап (P0 / P1 / P2) или крупная фича; внеплановые мелкие задачи — в
  постоянный `Maintenance`.

**Крупные фичи — через список задач в описании.** GitHub не имеет нативных эпиков; вместо
них используется issue-агрегатор с чек-листом подзадач (`- [ ] #123 …`) или GitHub Project
по договорённости. Подзадачи самодостаточны: в каждую копируется её фрагмент спеки + ссылка.

### 2.4 Исполнение

- **Вопросы — до старта.** Перед первым коммитом исполнитель перечисляет открытые вопросы
  к карточке одним списком и получает ответы. Вопрос, всплывший по ходу, оформляется как
  отклонение (§2.6), а не решается молча.
- Ветка от актуальной `main`: `feature/<issue>-<slug>` (или `fix/<issue>-<slug>` для багов).
- TDD для чистых функций из CODE-RULES §9.1: RED → GREEN → REFACTOR; RED-тест цитируется
  в PR как доказательство (§4).
- **PR — в `main`**; в описании указывается `Closes #N` для связки PR ↔ issue. Мерж PR —
  после зелёных проверок и пройденного ревью (§3).
- **Локальные проверки зелёные до создания PR:** `npm test` (когда есть), `npm start`
  (дымовой запуск), для изменений сборки/зависимостей — `npm run package` и запуск `.app`.
- Коммиты осмысленные, без мусора (`WIP`, `fix`, «чушь»). Секреты в коммит не попадают
  (AGENTS.md, «Секреты»).
- ⛔ Прямой push в `main` без PR — только для тривиальных правок (опечатка в README) и по
  явному решению владельца; всё остальное — через PR.

### 2.5 Ведение карточки

Карточка — живой документ на всём протяжении работы:

- пройденные пункты DoD отмечаются галочками по мере выполнения;
- **все отклонения от изначального плана** фиксируются комментарием: что изменилось и почему;
- при закрытии — итоговый комментарий: что сделано, отклонения, ссылка на PR, вердикт ревью.

**Исправление → правило.** Замечание владельца, которое обобщается за пределы карточки,
в тот же день становится нормой — в `CODE-RULES.md`, `UI-RULES.md` или здесь. Комментарий
в карточке правилом не считается. Нормативы прореживаются тем же тестом, каким пополняются:
строка остаётся, только если без неё будут ошибки.

## 3. Ревью

### 3.1 Ревью задачи

Каждая кодовая задача проходит ревью до закрытия. Первый вопрос ревью:
**реализовано ли в коде то, что требовалось задачей** (сверка с «Что нужно сделать» и спекой).

Ревью — по **факт-протоколу**:

- перед каждой находкой **читать реальный код** и давать ссылку `file:line`;
- находку, не подтверждённую в коде, помечать «НЕ ПРОВЕРЕНО» и не выдавать за факт;
- проверять: файл ≤ 700 строк (CODE-RULES §1); бизнес-логика не в `main.js`/IPC (§2.2);
  IPC-канал есть и в `registerIpc()`, и в `preload.js` (§3.2); пользовательский текст
  экранирован (§4.2); секреты/ключи не уходят в рендер и не логируются (§8);
  `~/.ssh/config` сохраняет чужой контент (§8.3); `execFile` с массивом, а не `exec`
  со строкой (§2.3);
- выносить только то, что влияет на корректность, требования карточки или нормы CODE-RULES;
  стилистика и вкусовые предпочтения — не выше `nit`;
- для задачи с UI — сверять нормы [`UI-RULES.md`](./UI-RULES.md) целиком, а не выборочно.

Вердикт ревью (что найдено / что починено) фиксируется комментарием в issue перед закрытием.

### 3.2 Гейт между этапами

Для поэтапной фичи (P0: терминал → вкладки → подключение → поиск → темы) каждый этап
проходит цикл и **не закрывается**, пока не пройден гейт:

> **RED (показан) → GREEN → локальные проверки зелёные → ревью (факт-протокол) →
> перепроверка находок → фикс блокеров → следующий этап.**

Блокеры (чинятся ДО перехода к следующему этапу):

- файл > 700 строк → разбить по смыслу;
- секрет/пароль/ключ в коде, конфиге, логе или фикстуре;
- ослабление `contextIsolation`/`nodeIntegration`/CSP;
- `exec` со строкой вместо `execFile`/`spawn` с массивом;
- пользовательский текст без `esc()` в HTML;
- новая переиспользуемая UI-часть, сделанная копией/инлайном вместо класса в `styles.css`.

### 3.3 Финальное ревью milestone / крупной фичи

После завершения всех подзадач и до закрытия агрегатора проводится полное ревью:
соответствие спеке по критериям приёмки, качество кода, безопасность (CODE-RULES §8),
проверка в собранном `.app`, вердикт — комментарием в агрегирующем issue.

## 4. Definition of Done

### 4.1 DoD кодовой задачи (базовый чеклист)

- [ ] Реализовано то, что требовалось задачей (сверка с описанием и спекой);
- [ ] Тесты: для чистых функций — RED→GREEN (CODE-RULES §9.1), красный вывод приведён;
- [ ] Локальные проверки зелёные: `npm test`, `npm start` (дым), `npm run package` при
      изменении сборки/зависимостей + запуск `.app`;
- [ ] Безопасность (CODE-RULES §8): приватный материал ключей не уходит в рендер; команды
      через массив аргументов; текст экранирован; секреты не в git/логах; CSP и границы
      процесса не ослаблены;
- [ ] UI (если есть): чек-лист UI-RULES §9.2 пройден, обе темы и минимальное окно проверены;
- [ ] Ревью пройдено, вердикт в карточке (§3.1);
- [ ] Карточка актуальна: галочки DoD проставлены, отклонения и итог зафиксированы (§2.5).

### 4.2 DoD bugfix

- [ ] Воспроизведение бага описано; тест (или шаги ручной проверки), воспроизводящий баг,
      приведён ДО исправления;
- [ ] Исправление не ломает соседний функционал (ручная проверка затронутых экранов);
- [ ] Остальное — по §4.1.

### 4.3 DoD некодовой задачи

Определяется при создании. Ориентиры:

- **documentation** — текст выверен, ссылки рабочие, нет устаревших утверждений;
- **research** — оформленный результат: документ в репозитории или развёрнутый вывод
  в карточке с рекомендацией (см. `docs/RESEARCH.md`, `docs/TERMINALS-RESEARCH.md`).

## 5. Labels и Milestones

### 5.1 Таксономия labels

| Группа | Labels | Правило |
|---|---|---|
| Тип | `bug`, `enhancement`, `documentation`, `chore`, `research`, `question` | Ровно один на задачу |
| Раздел | `area:main`, `area:renderer`, `area:security`, `area:storage`, `area:terminal`, `area:docs` | Один или несколько |
| Приоритет | `major`, `minor` | Максимум один; без label — обычный |

Правила:

- Label всегда покрывает **множество задач** — узкие labels (под одну задачу, конкретный баг)
  не создаются;
- Новый label создаётся, только когда под него есть ≥ 2 задачи;
- Разделы — по слоям приложения, а не по экранам интерфейса.

### 5.2 Milestones

- Milestone = этап дорожной карты (`P0 — встроенный терминал`, `P1`, `P2`) или крупная фича;
- Каждая задача привязана к milestone; внеплановые мелкие задачи — к постоянному `Maintenance`;
- Milestone закрывается после финального ревью (§3.3).

## 6. Релиз

Релиз — это сборка и публикация настольного приложения, а не деплой на сервер:

1. Мерж PR в `main` — после зелёных проверок и ревью;
2. Поднять `version` в `package.json` (semver) отдельным коммитом — по договорённости,
   не в каждом PR;
3. `npm run dist` — собрать `.dmg`/`.zip` в `dist/`;
4. Дымовая проверка собранного `.app` (запуск, ключевые сценарии);
5. Тег `vX.Y.Z` в GitHub по релизу — по договорённости.

Откат: коммит сломанного состояния ревертится обычным revert-коммитом; артефакты
`dist/` в git не хранятся (`.gitignore`).

## 7. Что изменилось против исходных правил BCS-TM-Platform

| Было (BCS-TM-Platform) | Стало (SSH Control) | Почему |
|---|---|---|
| GitLab Issues / MR / эпики группы | GitHub Issues / PR / чек-лист подзадач | Репозиторий и задачи — в GitHub |
| NestJS + Vue 3 + TypeScript + Drizzle + PG | Electron + plain JS (main/preload/renderer) | Другой стек: десктоп без бандлера |
| `service/` монорепо + `shared/` | один репозиторий, слои main/renderer | Нет общего расчётного слоя |
| OKD-деплой, Vault, Artifactory, helm | electron-builder → `.dmg`/`.zip` | Десктоп-приложение, а не веб-сервис |
| TypeScript strict, ESLint, пороги покрытия | `node:test`, конвенции plain-JS, ревью | Нет линтера/CI пока |
| Модель `model:*`, агент-ревьюер Opus | исполнитель + владелец, факт-протокол | Один разработчик |

Что **не** изменилось: атомарность задач (один PR на задачу), TDD для чистой логики,
факт-протокол ревью, ведение карточки как живого документа, «исправление → правило»,
DoD-чеклисты и запрет ослаблять границы безопасности.
