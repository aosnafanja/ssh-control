## Что это за проект

**SSH Control** — настольное приложение для macOS: хранилище SSH-ключей, данных серверов
и псевдонимов `~/.ssh/config` в едином современном интерфейсе. Не командный инструмент
с сервером, а локальное десктоп-приложение: всё работает на машине пользователя, без
своего бэкенда и без внешней сети.

Ключевая идея: данные о серверах живут в **одной переносимой папке** (`~/SSH Control/`),
а сами SSH-ключи остаются в `~/.ssh` — приложение читает их, создаёт и переименовывает
только по явной команде пользователя.

**Статус: работающий MVP.** Реализованы ключи (скан/создание/переименование/удаление),
псевдонимы (Host-блоки `~/.ssh/config`), серверы, мастер-пароль (AES-256-GCM + scrypt),
подключение через внешний Terminal.app. Следующий этап — **P0 встроенного терминала**
(xterm.js + node-pty): подключение внутри приложения, вкладки, поиск, темы
([`ROADMAP-terminal.md`](./docs/ROADMAP-terminal.md), [`PROMPT-P0.md`](./docs/PROMPT-P0.md)).

## Стек

- **Электрон:** Electron 45 (main + preload + renderer). Без бандлера, без TypeScript —
  обычный JavaScript. macOS-first.
- **Границы безопасности:** `contextIsolation: true`, `nodeIntegration: false`,
  `sandbox: false`; рендер общается с main только через узкий мост `window.api`
  (`preload.js`). CSP: `default-src 'self'; script-src 'self'` — никаких CDN и inline-скриптов.
- **Данные:** JSON-файл `data.json` в `~/SSH Control/`, опциональное шифрование
  AES-256-GCM с ключом из scrypt (N=16384, r=8, p=1) по мастер-паролю.
- **Тесты:** `node:test` (встроенный в Node ≥ 18), без порогов покрытия пока.
- **Сборка:** electron-builder → `.app` / `.dmg` / `.zip` (`build/` — только иконки).

## Структура репозитория

```
main/                привилегированный процесс (Node, доступ к ФС и системе)
  main.js              точка входа: окно, registerIpc(), жизненный цикл
  preload.js           мост window.api через contextBridge (тонкий, без логики)
  services/            модули по зонам ответственности
    keys.js              скан/создание/переименование/удаление ключей ~/.ssh
    sshConfig.js         чтение/редактирование ~/.ssh/config (Host-блоки)
    storage.js           data.json: загрузка/сохранение/шифрование
    connect.js           сборка команды ssh и запуск Terminal.app
renderer/            непривилегированный интерфейс (браузерный контекст)
  index.html            разметка экранов и навигация
  styles.css            токены (CSS-переменные), темы, классы
  app.js                состояние, рендер, обработчики (vanilla JS)
build/               иконки приложения (icon.icns, icon.svg, make_icon.py)
docs/                исследования, спеки, дорожные карты (см. README)
```

## Модель безопасности — нарушать нельзя

Это приложение работает с **самыми чувствительными данными пользователя**: приватными
SSH-ключами, паролями серверов и мастер-паролем. Поэтому границы ниже — инварианты,
а не рекомендации:

1. **Приватный материал ключей не покидает main-процесс.** Рендеру отдаются только
   метаданные: имя, тип, размер, отпечаток SHA256, публичный ключ, комментарий, mtime.
   Содержимое приватного ключа, пароль сервера и парольная фраза ключа через IPC не
   передаются никогда (CODE-RULES §2, §8).
2. **`contextIsolation: true` и `nodeIntegration: false` не ослабляются.** Единственный
   путь рендера к системе — явный обработчик `ipcMain.handle` + метод в `preload.js`.
   Никаких «выставить `nodeIntegration` ради удобства».
3. **CSP не расслабляется.** `script-src 'self'` означает: без CDN, без inline-скриптов,
   без `unsafe-inline` для script. Всё, что нужно рендеру (в т.ч. xterm.js), — локальными
   файлами внутри `renderer/` и должно попасть в `build.files`.
4. **Мастер-пароль хранится только как производный ключ.** Пароль нигде не сохраняется
   в открытом виде; расшифровка — только в памяти (`storage.js`). Параметры scrypt не
   понижаются.
5. **Секреты не пишутся в логи и в git.** Ни пароли, ни парольные фразы, ни содержимое
   ключей, ни содержимое `data.json`. `data.json` живёт вне репозитория
   (`~/SSH Control/`), `.gitignore` закрывает `node_modules/`, `dist/`, кэши.

Подробно правила secure coding — [`CODE-RULES.md`](./CODE-RULES.md) §8.

## Ограничения платформы — нарушать нельзя

Каждый пункт ломает либо работу приложения, либо собранный `.app`, причём чаще всего
молча:

- **Без бандлера.** Рендер грузит `app.js` и `styles.css` напрямую из `renderer/`.
  Любая зависимость рендера обязана быть обычным файлом внутри `renderer/` (или явно
  добавлена в `build.files` пакета). `node_modules` в собранное приложение **не входит**
  (см. `build.files` в `package.json`).
- **Нативные модули** (например, node-pty) должны быть собраны под версию Electron
  приложения (`electron-builder install-app-deps` / `@electron/rebuild`), иначе
  приложение падает на старте.
- **CSP `script-src 'self'`** — внешние CDN и inline-скрипты не проходят (см. выше).
- **`~/.ssh` — чужая территория.** Приложение не переписывает `~/.ssh/config` целиком:
  оно добавляет/правит только управляемые `Host`-блоки и сохраняет «чужой» контент
  (комментарии, `Include`, незнакомые опции) verbatim. См. `sshConfig.js`.
- **Пути из пользовательского ввода** не используются напрямую: имя ключа проходит
  `sanitizeName` (`keys.js`), путь к ключу строится внутри main.

## Секреты

⛔ **Секреты не коммитятся никогда** — ни в код, ни в фикстуры, ни в примеры. Пароль
сервера хранится в `data.json` (шифруется мастер-паролем), а не в репозитории.

⛔ **Секреты не логируются и не попадают в сообщения об ошибках**, которые видны
пользователю или в консоли: ни мастер-пароль, ни пароль сервера, ни парольная фраза,
ни содержимое приватного ключа.

✅ **Мастер-пароль** — только через scrypt + AES-256-GCM (`storage.js`). Пароль сервера
и парольная фраза ключа — тоже только в зашифрованном `data.json`; в открытом виде
они существуют лишь в момент использования.

Полные правила secure coding — [`CODE-RULES.md`](./CODE-RULES.md) §8.

## Локальный запуск и сборка

Нужен Node.js ≥ 18. Зависимости: Electron + electron-builder (devDependencies).

```bash
npm install          # один раз; если кэш npm с root-правами — см. README
npm start            # запуск приложения (electron .)
```

Проверка и сборка:

```bash
npm test             # unit-тесты node:test (когда скрипт добавлен — см. CODE-RULES §9)
npm run package      # папка .app в dist/
npm run dist         # .dmg и .zip в dist/
```

## Проверять решения на риски безопасности — до реализации

Каждое изменение, которое касается команд, путей, данных или IPC, прогонять по вопросам
**прежде чем** его делать. Примеры ниже — реальные места этого кода, а не гипотезы.

**Попадает ли пользовательский ввод в команду оболочки?** `connect.js` собирает команду
`ssh` из `extraArgs` — это осознанная power-user-функция, но она же и точка инъекции:
если команда выполняется через оболочку как строка, пользовательский текст
`; rm -rf …` исполнится. Правило: выполнять через `execFile`/`spawn` с **массивом
аргументов**, а не `exec` со строкой; `extraArgs` дополнительно ограничивается.

**Что уходит в рендер через IPC?** Добавляя обработчик, задавать вопрос: «нужны ли
рендеру именно эти данные?». Метаданные ключа — да; содержимое приватного ключа — нет.

**Не расширяем ли доверие к вводу?** Имя файла ключа приходит от пользователя в
`~/.ssh` — потому `sanitizeName` отбрасывает `../`, пробелы и прочие символы прежде,
чем имя превращается в путь.

**Попадёт ли секрет в лог?** `console.error` в рендере логирует ошибки — убедиться,
что в текст ошибки не попадает пароль/фраза/ключ.

**Отслеживается ли файл гитом?** `data.json` пользователя — вне репозитория; любые
тестовые данные с «реальными» ключами/паролями в фикстурах — запрещены.

Общее правило: если решение упрощает жизнь за счёт того, что чей-то секрет или чужой
файл оказываются в более открытом месте, — это не удобство, а перекладывание риска.
Такие места проговаривать явно, а не проносить молча.
